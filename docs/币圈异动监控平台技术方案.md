# 币圈异动监控平台技术方案

## 1. 当前定位

CryptoWatchtower 是一个基于 Go 的实时币圈异动监控平台。当前系统不做自动交易、不托管资金、不承诺收益，只提供市场数据采集、规则判断、风险提醒和运营观察能力。

当前代码主线已经从最初的 Binance 单交易所 MVP，演进到以下状态：

- Binance 默认启用：Spot/Futures WebSocket、Futures Funding REST。
- OKX 可选启用：Public WebSocket、Public REST instrument metadata。
- Telegram 默认频道告警已接入实时告警链路。
- Discord/Webhook 通知已作为可选渠道接入。
- PostgreSQL 持久化规则、告警相关事件、告警、通知日志和 Telegram chat 绑定信息。
- Redis 用于告警去重和限流。
- `/admin` 轻量运营后台已提供运行状态、列表过滤、规则编辑和趋势摘要。
- AI 15 分钟市场摘要已作为可选后台任务接入，默认关闭，摘要结果写入 PostgreSQL。

一句话目标：

> 先把多交易所实时监控、规则判断、通知链路和可选摘要任务跑稳，再逐步扩展用户体系和商业化能力。

## 2. 总体架构

系统采用 Go 模块化单体，部署上优先使用 Docker Compose，状态外置到 PostgreSQL 和 Redis。

```text
Binance WS / REST
OKX Public WS / REST
   ↓
collector / normalizer
   ↓
in-process eventbus
   ↓
rule engine
   ↓
alert pipeline
   ↓
Telegram / Webhook notifier

PostgreSQL:
  users / alert_rules / market_events / alerts / notification_logs / market_summaries / schema_migrations

Redis:
  dedupe keys / rate limit keys / short-lived state

HTTP:
  /health /api/v1/rules /api/v1/admin/* /admin
```

核心原则：

- 采集模块只负责交易所连接、字段解析和标准化。
- Rule Engine 只消费内部 `MarketEvent`，不直接依赖 Binance 或 OKX 原始 JSON。
- Notifier 只消费 `Alert`，不关心交易所原始字段。
- PostgreSQL 只保存告警链路相关事件，暂不保存全量成交流，避免早期写入压力过大。
- Redis 只用于短生命周期状态，不作为核心事实存储。

## 4. 模块设计

### 4.1 `config`

职责：

- 读取 YAML 配置。
- 支持环境变量覆盖。
- 启动时校验必要配置。

当前重点配置：

- `binance.enabled`
- `binance.spot_ws_base_url`
- `binance.futures_ws_base_url`
- `binance.futures_rest_base_url`
- `binance.symbols`
- `okx.enabled`
- `okx.public_ws_base_url`
- `okx.rest_base_url`
- `okx.symbols`
- `telegram.enabled`
- `telegram.bot_token`
- `telegram.default_chat_id`
- `webhook.enabled`
- `webhook.url`
- `summary.enabled`
- `summary.interval_sec`
- `summary.window_sec`
- `summary.max_items`
- `summary.provider`
- `summary.disclaimer`
- `summary.api_base_url`
- `summary.api_key`
- `summary.model`
- `summary.timeout_sec`
- `postgres.dsn`
- `redis.addr`
- `api.bearer_token`

### 4.2 `collector`

职责：

- 建立交易所 WebSocket 或 REST 连接。
- 处理订阅、心跳、重连和错误状态。
- 将交易所原始事件标准化为 `model.MarketEvent`。
- 将标准事件发布到 `eventbus`。

Binance 当前支持：

- Spot `aggTrade`
- Futures `aggTrade`
- Futures `forceOrder`
- Futures Funding REST `/fapi/v1/premiumIndex`

OKX 当前支持：

- Public WebSocket `trades`
- Public WebSocket `liquidation-orders`
- Public WebSocket `funding-rate`
- Public REST `/api/v5/public/instruments`

OKX swap 的 `sz` 是合约张数，名义金额必须结合 instrument metadata 的 `ctVal` 计算，不能直接按 `price * sz` 处理。

### 4.3 `eventbus`

当前采用进程内 channel，负责在 collector 和 rule pipeline 之间传递 `MarketEvent`。如果未来需要多实例或独立扩容，可替换为 Redis Stream、Kafka 或其他消息系统。

### 4.4 `rule`

职责：

- 根据 `MarketEvent` 生成 `Alert`。
- 支持默认阈值和数据库规则覆盖。
- 使用 Redis 做告警去重和限流。
- 在 pipeline 中写入事件、告警和通知日志。

当前规则类型：

- `large_trade`
- `large_trade_window`
- `liquidation`
- `funding_anomaly`

规则维度包含：

- `exchange`
- `symbol`
- `rule_type`

这保证 Binance 和 OKX 可以使用不同阈值。

### 4.5 `notifier`

职责：

- 将 `Alert` 格式化。
- 调用 Telegram Bot API 或 Webhook。
- 将每个渠道的投递结果写入 `notification_logs`。

当前 Telegram 投递方式：

- 实时告警发送到配置的 `telegram.default_chat_id`。
- `telegram.enabled=true` 且 `telegram.mode=polling` 时启用 Bot 命令。
- `/start` 会保存当前 chat_id，但真实告警当前仍使用默认 channel，不按绑定用户逐个投递。

当前 Webhook 投递方式：

- `webhook.enabled=true` 时启用。
- 发送 `{"content":"<formatted alert>"}` JSON。
- 任一渠道失败时仍会继续记录其他渠道投递结果，最后返回第一个发送错误。

### 4.6 `storage`

PostgreSQL 表：

- `users`
- `alert_rules`
- `market_events`
- `alerts`
- `notification_logs`
- `market_summaries`
- `schema_migrations`

注意：

- `market_events` 目前只保存触发告警链路的相关事件。
- `market_summaries` 保存每次 15 分钟摘要任务的窗口、provider、状态、正文和错误信息。
- `users.telegram_chat_id` 当前用于保存 Telegram `/start` 绑定结果。
- 后续用户级推送需要在 notification pipeline 中读取绑定用户并逐个发送。

### 4.7 `api` 和运营后台

当前 API：

- `GET /health`
- `GET /api/v1/symbols`
- `GET /api/v1/rules`
- `POST /api/v1/rules`
- `POST /api/v1/alerts/test`
- `POST /api/v1/telegram/test`
- `GET /api/v1/admin/overview`
- `GET /api/v1/admin/trends`
- `GET /api/v1/admin/rules`
- `GET /api/v1/admin/alerts`
- `GET /api/v1/admin/events`
- `GET /api/v1/admin/notifications`

`/admin` 页面能力：

- Bearer Token 输入。
- 中英语言切换。
- 运行状态展示。
- 24 小时概览与趋势摘要。
- Rules、Alerts、Events、Notifications 列表。
- exchange、symbol、rule_type、event_type、status、limit 过滤。
- 系统规则编辑。

当前后台是轻量运营台，不是完整用户侧 Dashboard。它没有账号登录、角色权限、分页翻页、图表化趋势和审计流。

## 5. 交易平台接入方案

### 5.1 Binance

当前 Binance 接入全部使用公开行情接口，不需要 API Key，也不需要注册 Binance 账户。

使用接口：

- Spot WebSocket base URL：`wss://stream.binance.com:9443/ws`
- Futures WebSocket base URL：`wss://fstream.binance.com/ws`
- Futures REST base URL：`https://fapi.binance.com`
- Spot/Futures aggTrade stream：`<symbol>@aggTrade`
- Futures liquidation stream：`<symbol>@forceOrder`
- Funding REST：`/fapi/v1/premiumIndex`

配置方式：

```yaml
binance:
  enabled: true
  spot_ws_base_url: "wss://stream.binance.com:9443/ws"
  futures_ws_base_url: "wss://fstream.binance.com/ws"
  futures_rest_base_url: "https://fapi.binance.com"
  symbols:
    - "BTCUSDT"
    - "ETHUSDT"
    - "SOLUSDT"
```

环境变量覆盖：

```bash
CW_BINANCE_ENABLED=true
CW_BINANCE_SYMBOLS=BTCUSDT,ETHUSDT,SOLUSDT
CW_BINANCE_SPOT_WS_BASE_URL=wss://stream.binance.com:9443/ws
CW_BINANCE_FUTURES_WS_BASE_URL=wss://fstream.binance.com/ws
CW_BINANCE_FUTURES_REST_BASE_URL=https://fapi.binance.com
```

### 5.2 OKX

当前 OKX 接入使用公开行情接口，不需要 API Key，也不需要注册 OKX 账户。

使用接口：

- Public WebSocket：`wss://ws.okx.com:8443/ws/v5/public`
- Public REST：`https://www.okx.com`
- Instrument metadata：`GET /api/v5/public/instruments?instType=SPOT`
- Instrument metadata：`GET /api/v5/public/instruments?instType=SWAP`
- Trades channel：`trades`
- Liquidation channel：`liquidation-orders`
- Funding channel：`funding-rate`

配置方式：

```yaml
okx:
  enabled: false
  public_ws_base_url: "wss://ws.okx.com:8443/ws/v5/public"
  rest_base_url: "https://www.okx.com"
  symbols:
    - "BTCUSDT"
    - "ETHUSDT"
    - "SOLUSDT"
```

环境变量覆盖：

```bash
CW_OKX_ENABLED=true
CW_OKX_SYMBOLS=BTCUSDT,ETHUSDT,SOLUSDT
CW_OKX_PUBLIC_WS_BASE_URL=wss://ws.okx.com:8443/ws/v5/public
CW_OKX_REST_BASE_URL=https://www.okx.com
```

当前限制：

- 只支持 USDT spot 和 USDT linear swap 的第一层接入。
- 启用 OKX 时启动阶段会先拉取 SPOT/SWAP instrument metadata，如果该 REST 请求失败，应用会启动失败。
- OKX live `trades` 频道可能出现交易所侧权限或交易等级限制，应该区分交易所限制和本地解析错误。

### 5.3 新增交易所的扩展边界

新增交易所不应改 Rule Engine 和 Notifier。推荐只新增：

- `internal/collector/<exchange>_ws.go`
- `internal/collector/<exchange>_rest.go`
- `internal/collector/<exchange>_normalizer.go`
- 配套测试文件
- 配置项和运行时 wiring

标准输出必须仍然是 `model.MarketEvent`。

## 6. Telegram 接入方案

Telegram 当前承担两类职责：

1. 告警投递：通过 `telegram.default_chat_id` 发到默认用户、群组或频道。
2. Bot 交互：通过 polling 支持 `/start`、`/status`、`/rules`、`/test`。

配置方式：

```yaml
telegram:
  enabled: true
  bot_token: "YOUR_BOT_TOKEN"
  default_chat_id: "YOUR_CHAT_ID"
  parse_mode: "Markdown"
  mode: "polling"
```

环境变量覆盖：

```bash
CW_TELEGRAM_BOT_TOKEN=YOUR_BOT_TOKEN
CW_TELEGRAM_DEFAULT_CHAT_ID=YOUR_CHAT_ID
```

当前限制：

- `parse_mode` 已在配置中保留，但发送 payload 当前未带 `parse_mode`。
- `/start` 保存 chat_id 后，真实告警仍然发送到 `default_chat_id`。
- 用户级订阅、退订、按规则订阅和静默时段尚未实现。

## 7. 部署方案

本地或单机部署推荐 Docker Compose：

```bash
docker compose -f deployments/docker-compose.yml up -d --build
```

如果本机 8080 被占用：

```bash
APP_HTTP_PORT=18080 docker compose -f deployments/docker-compose.yml up -d --build
```

健康检查：

```bash
curl http://127.0.0.1:8080/health
```

运营后台：

```text
http://127.0.0.1:8080/admin
```

生产部署建议：

- 单机 Docker Compose 起步。
- PostgreSQL 和 Redis 初期可同机，后续迁移到独立实例或托管服务。
- 使用 Nginx/Caddy/负载均衡器暴露 HTTP。
- Telegram token、API Bearer Token、数据库密码必须通过环境变量或密钥管理注入。
- 不要将真实 token、DSN 密码提交到 Git。

## 9. AI 市场摘要

AI Summary 当前作为独立后台任务存在，不进入实时 `rule.Pipeline`。启用后，调度器按配置间隔调用 summary service，service 从 PostgreSQL 读取有界 `alerts` 和 `market_events` 样本，生成包含“不构成投资建议”的摘要并写入 `market_summaries`。

关键边界：

- 默认关闭，`summary.enabled=false`。
- 默认 15 分钟执行一次，读取最近 15 分钟窗口。
- 默认最多读取 50 条 alert/event 样本，避免一次性加载大结果集。
- provider 支持 `template` 和 `openai_compatible`。
- 生成失败会写入 `failed` 摘要记录并记录错误，不影响 collector、HTTP 服务和实时告警。
- 持久化失败由 summary job 记录日志并继续后续 tick，不停止主服务。
- Admin UI 展示摘要记录可作为后续小步扩展。

配置示例：

```yaml
summary:
  enabled: false
  interval_sec: 900
  window_sec: 900
  max_items: 50
  provider: "template"
  disclaimer: "不构成投资建议"
  api_base_url: ""
  api_key: ""
  model: ""
  timeout_sec: 15
```

OpenAI-compatible provider 所需信息：

- `CW_SUMMARY_API_BASE_URL`
- `CW_SUMMARY_API_KEY`
- `CW_SUMMARY_MODEL`
- `CW_SUMMARY_TIMEOUT_SEC`

真实 API Key 必须通过环境变量或密钥管理注入，不能提交到 Git。
