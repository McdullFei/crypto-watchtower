# 币圈异动监控平台总体开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按阶段推进 CryptoWatchtower，从 Binance 单交易所生产闭环，到运营后台可视化，再到多交易所与 SaaS 增强能力。

**Architecture:** 继续采用 Go 模块化单体作为主干，围绕 collector、normalizer、event bus、rule engine、notifier、storage、admin API 明确边界。所有新增能力必须先接入可观测、可测试、可回滚的主链路，再扩展交易所、渠道和商业化功能。

**Tech Stack:** Go 1.24、PostgreSQL 16.14、Redis 7.0.15、Docker Compose、Binance WebSocket/REST、Telegram Bot API、原生 `net/http` 管理 API 与轻量 Admin UI。

---

## 1. 当前判断

当前项目已经具备 Phase 1 主体骨架：

- Binance Spot/Futures WebSocket 采集。
- Binance Futures Funding REST 拉取。
- 大单、爆仓、Funding、60 秒累计大单规则。
- Telegram 告警发送与 Bot polling 命令。
- PostgreSQL migration、Redis 去重与限流。
- `/health`、基础管理 API、轻量 `/admin` 后台。
- Dockerfile、Docker Compose、本地运行说明。

当前不建议立刻同时扩展多个交易所，也不建议直接进入复杂 SaaS 功能。最佳切口是先做 **Phase 1.5：Binance 生产闭环与可观测性收口**。

### Phase 1-B / Phase 2-B：第二交易所接入

**目标：** 用一个新增交易所验证多交易所抽象，而不是一次性接入多个平台。

**执行前置：** Phase 1.5 完成；Phase 2-A 至少完成健康状态、Events、Alerts、Notifications 展示。

**推荐顺序：**

1. 选择一个交易所：Bybit 或 OKX。
2. 只接入与 Binance Phase 1 对等的数据类型。
3. 复用现有事件模型和规则引擎。
4. 在后台和 API 增加 exchange 过滤。

**任务清单：**

- [ ] 固化 exchange collector 边界。
  - `Start(context.Context) error`
  - `Subscribe([]string) error`
  - `Status() collector.Status`
  - 标准化输出统一为 `model.MarketEvent`

- [ ] 选择并接入第二交易所。
  - 先完成 aggTrade 或等价成交流。
  - 再完成 liquidation 或等价爆仓流。
  - Funding 数据最后接入。

- [ ] 增加 normalizer 测试。
  - 使用真实样例 payload。

- [ ] 复用规则引擎。
  - `exchange` 成为规则匹配维度。

- [ ] 后台增加 exchange 可视化与过滤。

## 3. 横向工程约束

### 3.1 验证优先

每个阶段完成前必须给出验证证据：

- 单元测试。
- 集成测试。
- Docker Compose smoke test。
- `/health` 检查结果。
- 关键 API curl 示例。
- 必要时提供稳定性运行记录。

### 3.2 内存友好

后端实现默认避免 OOM 风险：

- 不全量加载大结果集。
- 列表查询必须限制 `limit`，并设置上限。
- 大事件流入库前必须评估写入频率、保留周期和查询索引。
- 批量任务优先分页、分批或流式处理。
- 长周期缓存必须有边界和释放策略。

### 3.3 安全边界

- 写接口必须鉴权。
- 真实 token、chat_id、DSN 不提交到仓库。
- 账号密码相关功能进入 Phase 3 时必须落实强密码后端校验。
- 对外文案必须保留“不构成投资建议”的声明。
