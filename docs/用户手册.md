# CryptoWatchtower 用户手册

## 1. 手册适用对象

本文面向部署者、运营人员和后续接入人员，说明 CryptoWatchtower 如何接入交易平台、如何配置 Telegram、如何启动服务、如何使用运营后台，以及日常排障时应该看哪些信息。

CryptoWatchtower 只提供实时市场数据监控和风险提醒，不做自动交易，不托管资金，不构成投资建议。

## 2. 当前能力概览

当前平台已经支持：

- Binance Spot/Futures 行情采集。
- Binance Futures Funding REST 定时拉取。
- OKX Spot/Swap 行情采集，默认关闭，可通过配置开启。
- 大单、60 秒累计大单、爆仓、Funding 异常规则。
- Telegram 默认频道告警。
- Discord/Webhook 可选通知。
- AI 15 分钟市场摘要可选任务，默认关闭。
- PostgreSQL 持久化告警相关事件、告警、规则和通知日志。
- Redis 告警去重和限流。
- `/admin` 轻量运营后台。
- `/dashboard` 用户侧 Web Dashboard。
- SaaS 基础账号能力：注册、登录、退出、密码重置、修改密码和 session cookie。
- Free / Pro / VIP 本地订阅权益边界。
- Telegram `/start <binding_token>` 账号绑定、解绑、用户规则个人投递、用户级累计窗口规则、用户通知日志、Telegram 投递开关、免打扰时段和摘要投递偏好。

当前还未完成：

- 真实支付计费、发票、组织账号和第三方 OAuth。

## 3. 本地启动平台

### 3.1 准备环境

需要安装：

- Docker Desktop 或 Docker Engine
- Docker Compose

推荐直接使用 Docker Compose 启动 PostgreSQL、Redis 和应用。

### 3.2 启动服务

在仓库根目录执行：

```bash
docker compose --env-file deployments/.env.local -f deployments/docker-compose.yml up -d --build
```

如果本机 8080 已被占用：

```bash
APP_HTTP_PORT=18080 docker compose --env-file deployments/.env.local -f deployments/docker-compose.yml up -d --build
```

### 3.3 检查健康状态

默认端口：

```bash
curl http://127.0.0.1:8080/health
```

自定义端口：

```bash
curl http://127.0.0.1:18080/health
```

健康响应中重点看：

- `data.status` 是否为 `up`
- `data.dependencies.postgres.status`
- `data.dependencies.redis.status`
- `data.collectors[].name`
- `data.collectors[].connected`
- `data.collectors[].last_error`

### 3.4 打开运营后台

浏览器打开：

```text
http://127.0.0.1:8080/admin
```

如果使用 18080：

```text
http://127.0.0.1:18080/admin
```

后台会要求填写 Bearer Token。默认示例配置是：

```text
change-me
```

生产环境必须修改 `api.bearer_token` 或 `CW_API_BEARER_TOKEN`。

### 3.5 打开用户侧 Dashboard

浏览器打开：

```text
http://127.0.0.1:8080/dashboard
```

如果使用 18080：

```text
http://127.0.0.1:18080/dashboard
```

页面提供注册、登录、退出、修改密码、个人规则、Telegram 绑定状态、Telegram 解绑、Telegram 投递开关、免打扰时段、摘要投递偏好、最近投递状态、套餐限额、个人告警历史和个人通知日志。用户侧 API 使用 `cw_session` HttpOnly Cookie 识别当前用户，不再需要在页面填写 Bearer Token 或显式 `user_id`。

账号密码相关操作执行后端强密码校验：至少 8 位，且必须同时包含大写字母、小写字母、数字和特殊字符。该规则适用于注册、密码重置确认和修改密码。

当前订阅权益是本地固定配置，不包含真实支付计费：

| 套餐 | 个人规则上限 | 告警历史上限 |
| --- | ---: | ---: |
| Free | 5 | 20 |
| Pro | 50 | 100 |
| VIP | 200 | 200 |

## 4. 配置文件和环境变量

默认配置文件：

```text
configs/config.example.yaml
```

推荐生产环境使用环境变量覆盖敏感信息：

```bash
CW_POSTGRES_DSN="postgres://postgres:CryptoWatchtower_Local_2026!@postgres:5432/crypto_watchtower?sslmode=disable"
CW_REDIS_ADDR="redis:6379"
CW_REDIS_PASSWORD="CryptoWatchtower_Local_2026!"
CW_TELEGRAM_BOT_TOKEN="YOUR_BOT_TOKEN"
CW_TELEGRAM_DEFAULT_CHAT_ID="YOUR_CHAT_ID"
CW_API_BEARER_TOKEN="change-me"
```

本地初始化密码已经写入 `configs/config.example.yaml` 和 `deployments/.env.local`，用于快速搭建项目；生产环境仍应替换 `deployments/.env.prod` 中的 `CHANGE_ME_*` 值。不要把真实 token、生产密码、生产 DSN 写入 Git。

## 5. 对接 Binance

### 5.1 是否需要注册 Binance

当前系统只读取 Binance 公开行情数据，不下单、不查账户、不使用私有接口。因此：

- 不需要 Binance API Key。
- 不需要注册 Binance 账户。
- 不需要开通交易权限。

如果后续要做私有账户数据、下单或用户资产相关功能，才需要注册账户并创建 API Key。当前版本不要配置 Binance API Key。

### 5.2 Binance 当前接入的数据

当前接入：

- Spot `aggTrade`
- Futures `aggTrade`
- Futures `forceOrder`
- Futures Funding REST

默认交易对：

```text
BTCUSDT
ETHUSDT
SOLUSDT
```

### 5.3 Binance 配置步骤

1. 打开配置文件 `configs/config.example.yaml`。
2. 确认 `binance.enabled` 为 `true`。
3. 确认 WebSocket 和 REST 地址可访问。
4. 在 `binance.symbols` 中配置要监控的交易对。
5. 重启服务。
6. 访问 `/health`，确认 `binance-spot`、`binance-futures` 出现在 collectors 中。

配置示例：

```yaml
binance:
  enabled: true
  spot_ws_base_url: "wss://stream.binance.com:9443/ws"
  futures_ws_base_url: "wss://fstream.binance.com/ws"
  futures_rest_base_url: "https://fapi.binance.com"
  symbols:
    - "BTCUSDT"
    - "ETHUSDT"
    - "SOLUSDT"
```

环境变量示例：

```bash
CW_BINANCE_ENABLED=true
CW_BINANCE_SYMBOLS=BTCUSDT,ETHUSDT,SOLUSDT
```

## 6. 对接 OKX

### 6.1 是否需要注册 OKX

当前系统只读取 OKX 公开行情数据，不下单、不查账户、不使用私有接口。因此：

- 不需要 OKX API Key。
- 不需要注册 OKX 账户。
- 不需要开通交易权限。

如果后续要做私有账户数据、下单或用户资产相关功能，才需要注册账户并创建 API Key。当前版本不要配置 OKX API Key。

### 6.2 OKX 当前接入的数据

当前接入：

- Spot `trades`
- Swap `trades`
- Swap `liquidation-orders`
- Swap `funding-rate`
- Public REST instruments metadata

OKX swap 的数量字段是合约张数。系统会先通过 instrument metadata 获取 `ctVal`，再计算名义金额。

### 6.3 OKX 配置步骤

1. 打开配置文件 `configs/config.example.yaml`。
2. 将 `okx.enabled` 改为 `true`。
3. 确认 `okx.public_ws_base_url` 为 OKX Public WebSocket 地址。
4. 确认 `okx.rest_base_url` 为 OKX Public REST 地址。
5. 在 `okx.symbols` 中配置交易对，使用 `BTCUSDT` 这种紧凑格式。
6. 重启服务。
7. 访问 `/health`，确认 `okx-public` 出现在 collectors 中。

配置示例：

```yaml
okx:
  enabled: true
  public_ws_base_url: "wss://ws.okx.com:8443/ws/v5/public"
  rest_base_url: "https://www.okx.com"
  symbols:
    - "BTCUSDT"
    - "ETHUSDT"
    - "SOLUSDT"
```

环境变量示例：

```bash
CW_OKX_ENABLED=true
CW_OKX_SYMBOLS=BTCUSDT,ETHUSDT,SOLUSDT
CW_OKX_PUBLIC_WS_BASE_URL=wss://ws.okx.com:8443/ws/v5/public
CW_OKX_REST_BASE_URL=https://www.okx.com
```

### 6.4 OKX 常见问题

如果应用启动失败并看到 instrument 相关错误，优先检查：

- 服务器是否能访问 `https://www.okx.com`。
- DNS 和代理配置是否正常。
- OKX Public REST 是否被网络或地区限制。

如果 `/health` 中 `okx-public.last_error` 有连接错误，但 HTTP 服务仍然 `up`，说明 WebSocket collector 出错但主服务仍在运行。

## 7. 注册和对接 Telegram

### 7.1 注册 Telegram 账号

1. 安装 Telegram 客户端。
2. 使用手机号注册或登录 Telegram。
3. 完成必要的安全设置。

### 7.2 创建 Telegram Bot

1. 在 Telegram 中搜索官方机器人 `@BotFather`。
2. 向 `@BotFather` 发送：

```text
/newbot
```

3. 按提示输入 Bot 显示名称。
4. 按提示输入 Bot 用户名，用户名通常需要以 `bot` 结尾。
5. `@BotFather` 会返回 Bot Token。
6. 保存 token，并通过环境变量注入到服务，不要提交到 Git。

环境变量：

```bash
CW_TELEGRAM_BOT_TOKEN="YOUR_BOT_TOKEN"
```

### 7.3 获取 default_chat_id

当前实时告警会发送到 `telegram.default_chat_id`。这个值可以是用户、群组或频道。

#### 方式一：个人聊天

1. 打开刚创建的 Bot。
2. 向 Bot 发送任意消息，例如：

```text
/start
```

3. 调用 Telegram `getUpdates` 查看 chat id。

示例：

```bash
curl "https://api.telegram.org/bot<YOUR_BOT_TOKEN>/getUpdates"
```

4. 在返回 JSON 中查找：

```text
message.chat.id
```

5. 将该值配置为：

```bash
CW_TELEGRAM_DEFAULT_CHAT_ID="123456789"
```

#### 方式二：群组

1. 创建 Telegram 群组。
2. 将 Bot 加入群组。
3. 在群组中发送一条消息，例如 `/start`。
4. 调用 `getUpdates`。
5. 找到群组对应的 `message.chat.id`，通常是负数。
6. 配置为 `CW_TELEGRAM_DEFAULT_CHAT_ID`。

#### 方式三：频道

1. 创建 Telegram Channel。
2. 将 Bot 添加为频道管理员，至少需要发消息权限。
3. 如果频道有公开用户名，可以尝试使用：

```text
@your_channel_name
```

作为 `default_chat_id`。

4. 如果使用数字 chat id，需要让频道产生一条可被 Bot 看到的更新，再通过 `getUpdates` 或 Telegram Bot API 调试获取。

### 7.4 配置 Telegram

YAML 示例：

```yaml
telegram:
  enabled: true
  bot_token: "YOUR_BOT_TOKEN"
  default_chat_id: "YOUR_CHAT_ID"
  parse_mode: "Markdown"
  mode: "polling"
```

环境变量示例：

```bash
CW_TELEGRAM_BOT_TOKEN="YOUR_BOT_TOKEN"
CW_TELEGRAM_DEFAULT_CHAT_ID="YOUR_CHAT_ID"
```

### 7.5 测试 Telegram 推送

启动服务后执行：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/telegram/test \
  -H "Authorization: Bearer change-me"
```

如果使用 18080：

```bash
curl -X POST http://127.0.0.1:18080/api/v1/telegram/test \
  -H "Authorization: Bearer change-me"
```

如果收不到消息，检查：

- `CW_TELEGRAM_BOT_TOKEN` 是否正确。
- `CW_TELEGRAM_DEFAULT_CHAT_ID` 是否正确。
- Bot 是否被用户启动过。
- Bot 是否在群组或频道中有发消息权限。
- 服务日志中是否有 `telegram request failed`。

### 7.6 Bot 命令

如果 `telegram.enabled=true` 且 `telegram.mode=polling`，Bot 支持：

```text
/start                  保存当前 chat_id，兼容默认通道调试
/start <binding_token>  将当前 chat_id 绑定到登录用户账号
/status                 查看服务状态摘要
/rules                  查看当前启用规则
/test                   回发一条测试告警
```

用户在 Dashboard 生成绑定 token 后，把 `/start <binding_token>` 发给 Bot。绑定成功后，个人规则命中的告警会发送到该用户绑定的 Telegram chat，并写入带 `user_id` 的通知日志。

## 8. 使用运营后台

### 8.1 登录后台

1. 打开 `/admin`。
2. 在左侧 Bearer Token 输入框中填写 `api.bearer_token`。
3. 点击刷新。

### 8.2 查看运行状态

Runtime Status 区域展示：

- app 状态
- PostgreSQL 状态
- Redis 状态
- Binance collector 状态
- OKX collector 状态
- 重连次数
- 最近事件时间
- 最近错误

### 8.3 使用列表过滤

左侧筛选区支持：

- `exchange`
- `symbol`
- `event_type`
- `rule_type`
- `status`
- `limit`

筛选后点击刷新，Rules、Alerts、Events、Notifications 会一起更新。

### 8.4 修改系统规则

Rule Editor 支持修改系统规则：

- Exchange
- Symbol
- Rule Type
- Threshold
- Window Sec
- Enabled

保存后规则会写入数据库，并立即应用到运行中的 Rule Engine。

常用规则类型：

- `large_trade`
- `large_trade_window`
- `liquidation`
- `funding_anomaly`

### 8.5 查看通知日志

Notifications 面板展示每次通知投递结果：

- `channel`
- `target`
- `status`
- `created_at`

如果开启多个通知渠道，每个渠道都会写一条独立日志。

## 9. 常用 API

健康检查：

```bash
curl http://127.0.0.1:8080/health
```

查看 symbols：

```bash
curl http://127.0.0.1:8080/api/v1/symbols
```

查看规则：

```bash
curl http://127.0.0.1:8080/api/v1/rules
```

更新规则：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/rules \
  -H "Authorization: Bearer change-me" \
  -H "Content-Type: application/json" \
  -d '{"exchange":"binance","symbol":"BTCUSDT","rule_type":"large_trade","threshold":120000,"enabled":true}'
```

查看用户自定义规则：

```bash
curl "http://127.0.0.1:8080/api/v1/rules?user_id=42"
```

写入用户自定义规则：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/rules \
  -H "Authorization: Bearer change-me" \
  -H "Content-Type: application/json" \
  -d '{"user_id":42,"exchange":"binance","symbol":"BTCUSDT","rule_type":"large_trade","threshold":120000,"enabled":true}'
```

说明：

- 不带 `user_id` 时写入系统规则，并立即应用到运行中的 Rule Engine。
- 带 `user_id` 时写入 `scope=user` 的用户规则；这是运营侧 Bearer Token API，用于后台管理或调试。
- 用户侧 Dashboard 使用 `/api/v1/user/*` 接口，由 `cw_session` Cookie 推导当前用户，不接收页面手填 Bearer Token。

### 9.1 用户侧账号与 Dashboard API

注册并写入 session cookie：

```bash
curl -i -X POST http://127.0.0.1:8080/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"Strong1!"}'
```

登录并保存 Cookie：

```bash
curl -c cookies.txt -X POST http://127.0.0.1:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"Strong1!"}'
```

退出登录：

```bash
curl -b cookies.txt -X POST http://127.0.0.1:8080/api/v1/auth/logout
```

申请密码重置。开发环境如果启用 `auth.expose_reset_token_in_dev=true` 会返回 `reset_token`；生产环境只返回泛化受理结果，不暴露账号是否存在：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/auth/password-reset/request \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com"}'
```

确认密码重置：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/auth/password-reset/confirm \
  -H "Content-Type: application/json" \
  -d '{"token":"RESET_TOKEN_FROM_DEV_RESPONSE","new_password":"Better1!"}'
```

登录后修改密码：

```bash
curl -b cookies.txt -X POST http://127.0.0.1:8080/api/v1/user/password \
  -H "Content-Type: application/json" \
  -d '{"current_password":"Strong1!","new_password":"Better1!"}'
```

查看用户侧 Telegram 绑定状态、套餐和限额：

```bash
curl -b cookies.txt "http://127.0.0.1:8080/api/v1/user/profile"
```

响应包含 `telegram_delivery_enabled`、`notification_preferences` 和 `recent_delivery_status`，页面据此展示 Telegram 投递开关、免打扰时段、摘要投递偏好和最近一次投递状态。

生成用户侧 Telegram 绑定 token：

```bash
curl -b cookies.txt -X POST http://127.0.0.1:8080/api/v1/user/telegram/binding-token
```

将响应里的 `token` 发给 Telegram Bot：

```text
/start <token>
```

绑定后，用户侧个人规则命中会投递到该用户绑定的 Telegram chat。禁用用户和未绑定用户不会触发个人 Telegram 投递。

关闭或开启用户侧 Telegram 投递：

```bash
curl -b cookies.txt -X PUT http://127.0.0.1:8080/api/v1/user/telegram/delivery \
  -H "Content-Type: application/json" \
  -d '{"enabled":false}'
```

关闭投递不会删除 Telegram 绑定。关闭期间个人规则命中仍会写入用户告警和通知日志，通知日志状态为 `disabled`，不会向 Telegram 发送消息。

配置用户侧 Telegram 免打扰时段和摘要模式：

```bash
curl -b cookies.txt -X PUT http://127.0.0.1:8080/api/v1/user/telegram/preferences \
  -H "Content-Type: application/json" \
  -d '{"telegram_quiet_hours_enabled":true,"telegram_quiet_hours_start":"23:00","telegram_quiet_hours_end":"07:00","telegram_quiet_hours_timezone":"Asia/Shanghai","telegram_digest_enabled":true,"telegram_digest_interval_min":60}'
```

免打扰时段按用户显式时区判断，只影响用户规则 Telegram 投递，不影响运营后台 Bearer Token 通知和默认系统通知。免打扰期间命中的用户规则会写入 `quiet_hours` 通知日志并跳过发送。

摘要模式启用后，用户规则命中的告警会按用户、时间窗口和最大条数有界累计，先写入 `digested` 通知日志，再由定时任务发送一条摘要 Telegram。摘要模式不会改变个人规则匹配、告警入库和通知日志入库行为。

解绑当前用户 Telegram：

```bash
curl -b cookies.txt -X DELETE http://127.0.0.1:8080/api/v1/user/telegram/binding
```

解绑只清空当前 session 用户的 `telegram_chat_id`，不会修改 `telegram_delivery_enabled` 偏好。

查看用户侧个人规则：

```bash
curl -b cookies.txt "http://127.0.0.1:8080/api/v1/user/rules"
```

写入用户侧个人规则：

```bash
curl -b cookies.txt -X POST http://127.0.0.1:8080/api/v1/user/rules \
  -H "Content-Type: application/json" \
  -d '{"exchange":"binance","symbol":"BTCUSDT","rule_type":"large_trade","threshold":120000,"window_sec":60,"enabled":true}'
```

用户侧支持 `large_trade_window`。该规则使用按用户和规则隔离的窗口状态，不复用系统规则窗口。

查看用户侧个人告警历史：

```bash
curl -b cookies.txt "http://127.0.0.1:8080/api/v1/user/alerts?limit=20"
```

个人告警历史通过 `notification_logs.user_id` 关联 `alerts.id` 查询，只展示已有用户通知归属的告警。

查看用户侧个人通知日志：

```bash
curl -b cookies.txt "http://127.0.0.1:8080/api/v1/user/notifications?limit=20"
```

通知日志响应包含 `channel`、脱敏后的 `target`、`status`、`error_message`、`alert_id` 和 `created_at`。该接口从 session 推导用户身份，即使传入 `user_id` 也不会读取其它用户数据。

查看后台告警：

```bash
curl "http://127.0.0.1:8080/api/v1/admin/alerts?limit=20&exchange=okx&symbol=BTCUSDT" \
  -H "Authorization: Bearer change-me"
```

查看后台通知日志：

```bash
curl "http://127.0.0.1:8080/api/v1/admin/notifications?limit=20&status=sent" \
  -H "Authorization: Bearer change-me"
```

## 10. 启用 Webhook 通知

Webhook 默认关闭。启用后会与 Telegram 一起复用告警链路。

配置：

```yaml
webhook:
  enabled: true
  url: "https://discord.com/api/webhooks/..."
  channel: "discord"
  timeout_sec: 10
```

环境变量：

```bash
CW_WEBHOOK_ENABLED=true
CW_WEBHOOK_URL="https://discord.com/api/webhooks/..."
CW_WEBHOOK_CHANNEL=discord
CW_WEBHOOK_TIMEOUT_SEC=10
```

注意：

- Webhook URL 属于敏感信息，不要提交到 Git。
- Telegram 失败不会阻止 Webhook 尝试投递，反过来也一样。
- 每个渠道都会写入独立 `notification_logs`。

## 11. 启用 AI 市场摘要

AI 市场摘要默认关闭。启用后，服务会按配置间隔读取已落库的 `alerts` 和 `market_events` 有界样本，生成带有“不构成投资建议”的摘要，并写入 `market_summaries` 表。

### 11.1 本地 template 摘要

本地验证建议先使用 deterministic template provider，不需要外部 API Key：

```yaml
summary:
  enabled: true
  interval_sec: 900
  window_sec: 900
  max_items: 50
  provider: "template"
  disclaimer: "不构成投资建议"
  api_base_url: ""
  api_key: ""
  model: ""
  timeout_sec: 15
```

环境变量：

```bash
CW_SUMMARY_ENABLED=true
CW_SUMMARY_PROVIDER=template
CW_SUMMARY_INTERVAL_SEC=900
CW_SUMMARY_WINDOW_SEC=900
CW_SUMMARY_MAX_ITEMS=50
CW_SUMMARY_DISCLAIMER="不构成投资建议"
```

### 11.2 OpenAI-compatible 摘要

如果要对接 OpenAI-compatible 服务，需要准备：

- API Base URL，例如 `https://api.example.com/v1`。
- API Key。
- 模型名称。
- 请求超时时间。

环境变量：

```bash
CW_SUMMARY_ENABLED=true
CW_SUMMARY_PROVIDER=openai_compatible
CW_SUMMARY_API_BASE_URL="https://api.example.com/v1"
CW_SUMMARY_API_KEY="YOUR_SUMMARY_API_KEY"
CW_SUMMARY_MODEL="YOUR_SUMMARY_MODEL"
CW_SUMMARY_TIMEOUT_SEC=15
```

注意：

- API Key 必须通过环境变量或密钥管理注入，不要提交到 Git。
- 摘要任务失败不会停止 collector、HTTP 服务或实时告警。
- 当前版本摘要已入库，后台页面展示摘要记录属于后续扩展。

## 12. 日常排障

### 12.1 服务启动失败

检查：

- PostgreSQL DSN 是否正确。
- Redis 地址是否正确。
- Redis 密码是否与 `REDIS_PASSWORD` / `CW_REDIS_PASSWORD` 一致。
- `api.bearer_token` 是否配置。
- 启用 Telegram 时 token 和 default_chat_id 是否配置。
- 启用 OKX 时是否能访问 OKX Public REST。
- 启用 `openai_compatible` 摘要时，summary API URL、API Key、model 是否配置。

### 12.2 collector 未连接

检查 `/health` 中：

- `connected`
- `reconnects`
- `last_error`
- `subscribed`

如果只有某个 collector 失败，但 HTTP 仍然 `up`，说明主服务仍可用。

### 12.3 告警太多

处理方式：

- 提高对应规则 threshold。
- 缩小 monitored symbols。
- 检查 Redis 是否正常，避免去重/限流失效。

### 12.4 没有告警

检查：

- collector 是否 connected。
- 规则 threshold 是否过高。
- `alert_rules` 是否禁用了对应规则。
- Telegram/Webhook 是否配置。
- 通知日志是否出现 failed。

## 13. 安全注意事项

- 不要提交 Telegram Bot Token。
- 不要提交 Discord/Webhook URL。
- 不要提交生产数据库密码。
- 生产环境必须修改默认 Bearer Token。
- 当前系统没有完整账号权限体系，不应直接暴露到公网裸奔。
- 如果需要公网访问 `/admin`，必须放在反向代理、访问控制或 VPN 后面。
